## 2. D4 具体契约建议

### 2.1 路径、格式与所有权

- 路线仍为 `claude-user`；实际根目录使用检测/锁定的 Claude 配置目录（支持 `CLAUDE_CONFIG_DIR`），默认 `~/.claude`。新增静态槽位名 `claude_rules`，与旧 `claude_md` 区分。
- 一个有效静态包对应 `rules/style-<包名>.md`；正文按现有编译结果和包内顺序拼接，保留跨包去重后的唯一保留方。没有有效静态正文的包不生成空文件。
- 保留编译器的正文顺序和去重选择；用户 rules 与其他 memory 的实际加载次序在 C1/C3 记录，不额外承诺高于用户自有或项目指令。若该次序差异导致不兼容，回到 D4 评审，不通过改文件名抢优先级。
- 文件用确定性的 STYLE 注释头尾标明格式版本和包名，包正文作为中间内容；不生成 `paths` frontmatter、不增加匹配条件，不修改用户自己的 rules。文件内容由 STYLE 整体管理；新文件权限 0644，已管理文件更新保留其权限。
- 文件名相同不足以证明归属。只有安装记录确认归属、格式/包名正确且字节与批准的生成内容一致，才能更新或删除。旧锁没有 rules 归属时不接管已有文件，即使正文相同也视为冲突。
- 冷路径安装/批准记录保存静态布局及生成文件摘要，旧记录按 `claude_md` 解释；不改 runtime index format、repeat 状态键或热路径。具体 Go 类型属于 T40 实现选择，兼容与语义由本节约束。

### 2.2 迁移时机与批准

升级二进制本身不改文件。第一次成功重建 Claude 路线的 `install`、`sync`、`trust` 或 `uninstall`，在同一变更计划中迁移仍生效的已批准静态包：生成新的 rules 文件，删除旧 `CLAUDE.md` 中对应托管块。卸载目标直接删除其托管内容，不为它创建新文件。

**单纯的载体迁移不追加一次 trust。** 输入正文、静态 append 语义和用户级作用域没有变化；报告明确展示旧路径、新路径和包名。已有的普通包源码变动、开发链接首次批准、native 变化及 replace 授权规则继续生效。`trust <name>` 只批准指定包；其他未批准包只使用已批准快照生成迁移内容，不顺带批准新源码或新命令。

迁移不是独立新命令，不引入全局 `--yes` 或 `--allow-replace` 绕过冲突。只读 `plan`、`list`、`adapters`、`doctor` 和 `stats` 不迁移文件；`doctor` 能报告旧布局待迁移，但仍认同升级前的有效安装。

### 2.3 冲突、失败与往返保证

- 先读取/校验完整目标集合。目的文件由用户/其他工具占用、已有管理文件被改写、旧标记损坏/重复/嵌套、路径经过 symlink、不可读/不可写等情况，停止本次变更并退出 1，说明相关路径；不覆盖、不删除外部文件，也不悄悄退回另一载体。
- 原旧块只能按现有 owner/marker 解析删除，托管区外的用户字节、换行和权限保持。目的文件准备失败时不先删旧块；应用前再次核对快照，计划后被修改的文件拒绝覆盖。
- 由 Claude adapter 产出外部文件变化，复用现有 `agenthooks/install.ApplyFiles` 的单文件 rename、失败回滚与路径检查；app 继续把配置、index、lock 和批准快照交给现有安装事务。无需新增规则引擎或移动 agenthooks 的归属职责。若现有路径检查无法表达 nested rules 文件，T40 应只补必要范围并补对应测试。
- 普通执行失败走现有回滚，回滚失败要显式报错；不承诺进程崩溃时多文件更新具备数据库式原子性。
- 最终卸载只删除已确认归属且未漂移的 rules 文件、旧 STYLE 块和 STYLE hook；用户原文件字节及权限还原，不递归清理 rules 目录。原本不存在且仅由 STYLE 创建的 `CLAUDE.md` 清空后删除，遵循现有生命周期。
- 检测到已管理 rules 文件漂移时保留它，先由用户恢复批准版本或解决冲突；本次 M2 不新增自动收养/强制覆盖开关。迁移后重新使用旧二进制可能重新创建旧块，自动降级不在契约内。

### 2.4 A7/C3 验收建议

A7 按本节细化。至少覆盖：

1. 两个静态包与一个纯动态包的全新安装；自定义配置目录；只生成两份 rules，hook/index 与正文成本口径正确。
2. 旧二进制生成的旧安装升级，分别经 install/sync/trust/uninstall 触发；迁移后正文不同时残留于旧块与新文件，重复 sync 幂等。原 `CLAUDE.md` 使用 LF、CRLF、无末尾换行及 Unicode 固定 fixture，外部字节/权限精确还原。

5. 新旧布局的 list/doctor、旧锁兼容、仅静态安装、最后一个包卸载、其他工具规则和 native handler 保留；三路线 conformance、双 module test/vet、相关 race、build/smoke 通过。

## 3. D5 具体契约建议

维持两家 adapter 的 `StaticLocation("replace")` 不可用，不写 output style 文件、不改 `outputStyle` 选择，也不新增样式合并策略。

| 前提 | 预期结果 |
|---|---|
| `mode: replace` + `fallback: degrade` / `skip` | plan 为 `skipped`，无 placement；不以动态追加冒充替换 |
| `mode: replace` + `fallback: error` | plan 为 `install-error` / blocked，退出 4，安装不写入 |
| 已有 `--allow-replace` / 交互批准 | 仅满足现有授权检查，不使 adapter 获得替换能力 |
| 安装时缺少现有 replace 授权 | 保持原授权错误与退出码 1，不改成能力错误 |

本次已评审通过；完成 A8 验证后，T50 可记录为“按 D5 不实现 output style 替换”；A8 改验已有 fallback 与不写样式/设置的保证，使用实际 fixture/CLI 结果关闭，不能只标“不适用”而无证据。现有可复用测试有 `core/plan/plan_test.go` 的 `TestBuildRejectsReplaceWhenStaticLocationIsUnavailable`、Claude adapter 的 replace 槽位断言，以及 app 的 replace 授权测试。现有测试已覆盖 degrade/error，skip 与样式设置不变的真实 CLI 证据在关闭 A8 前补齐。

C4 的用户界面切换/冲突观察继续保留 `[~]`，不能用“不实现”将未执行的界面步骤标成功。若今后希望提供独立的 output style 管理功能，应另外定义其用途和用户已有样式的归属；不放进本次 replace。
