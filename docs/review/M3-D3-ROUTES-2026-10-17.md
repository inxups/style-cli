## 2. 范围选择与命令

默认继续操作当前用户根。新增值必填的 `--project <dir>`（也接受 `--project=<dir>`），明确选择一个项目根；不因当前目录里有仓库就自动切换范围，也不把随后的来源位置参数当成项目路径。给定目录必须存在，解析为绝对规范路径；允许显式非 Git 项目，不调用 Git 猜根。项目根不允许等于用户安装根、harness 用户配置目录或其受保护子目录。

| 命令组 | 提案 |
|---|---|
| plan/install/list/sync/trust/update/uninstall/doctor/stats/probe | 接受同一 `--project <dir>`；省略时用户级；所有隐式根和修改目标都来自选中的范围 |
| install --frozen | 接受范围选择；仍整锁、离线、不改来源/设置/绑定、不迁移，不允许用另一 clone 的根代替当前绑定 |
| explain | 接受范围以选择默认 index/provenance/state snapshot；显式离线输入仍遵守 D1 隔离与只读契约 |
| adapters | 可用项目范围查询路线与前提；`auto` 只在当前范围的候选路线中选择 |
| validate/init/tokens | 保持原来包级语义；本轮不增加隐式项目安装或跨范围查询 |
| export | T31 新增 `style export --target claude-cloud --project <dir> [--yes] [--json]`，只导出本范围已批准的 Claude 交付产物 |

示意（尚未实现）：

```sh
style plan ./style-pack --project /work/repo --harness codex,claude-code
style install ./style-pack --project /work/repo --yes
style list --project /work/repo
style update --all --project /work/repo --yes
style install --frozen --project /work/repo --yes
style probe --project /work/repo --harness claude-code
style export --target claude-cloud --project /work/repo --yes
style uninstall --all --project /work/repo
```

不引入隐式 user/project 合并安装、同名覆盖或跨范围 `--all`。输出增加范围、规范项目根、安装根、路线及 external prerequisites；JSON 成功/失败的既有格式与退出码约定保持，新增范围错误为退出 1，规划阻断仍为 4，sync 漂移仍为 3。新增字段只在新范围/路线报告使用，旧调用的已有 golden 不无故改写。

## 3. 存储、根身份与兼容

设 `U` 为既有 `--style-home` / `STYLE_HOME` / `~/.style` 解析出的用户管理基根；`R` 为规范项目路径；`H = SHA256(UTF-8(R))`，使用完整小写十六进制。项目安装根为 `U/projects/H/`，目录权限 0700，内部沿用 packages、approved、settings、style.lock.yaml、build、state、cache、probes 布局。hash 只用来命名，不是匿名化或授权证明；私有 binding 中保留 R 并核对，路径哈希碰撞或 root 不一致立即拒绝。

项目文件只有可移植的 `.style/project.json` 声明、`.style/hooks/` 启动器及 harness 项目配置/静态产物。声明 format=1，记录生成器入口版本、受管相对路径与 STYLE 区域/完整生成文件的摘要，不保存本机路径、用户根、凭据、settings、批准快照或“已信任”字段。根声明本身不授权执行；本地仍要求该 clone 在私有安装根有完成的 binding 和 lock。模板文件/启动器归属由私有安装快照管理；遇到无归属的同名文件、symlink、漂移或损坏标记拒绝接管。

首次激活新 clone 有一条明确例外：普通 install 必须从用户明确提供的来源重新生成全部候选，逐项证明仓库声明、STYLE 区域和生成文件与候选完全一致，再在完整预览/确认中将这些既有 STYLE 效果纳入本 clone 所有权。仅有仓库声明或 --frozen 不足以采用；任何摘要/事件/原文不同、缺项或外来同名文件都拒绝。此过程重新确认本 clone 的 native/能力，不能继承另一 clone 的批准/信任。采用的 STYLE 区域卸载时移除，托管区之外的基线字节保留，预览必须说明这一点；不得将旧仓库中的 STYLE 区域作为“外部基线”恢复而留下规则。此例外只适用于有可重现声明的新项目激活，不放宽旧用户路线的 owner 规则。

不同 clone、worktree 和不同目录使用独立 H、lock、index、seq、state、stats、probe、cache；同名包在两个项目中互不影响。移动目录、改根、改 STYLE_HOME 要显式重新安装；不能把旧 state 或信任当作可搬运物。符号链接别名归同一规范根，但 Codex hook 信任只支持规范路径启动，doctor 必须提示实际别名键不足，不自动枚举和批准所有别名。

这里的 worktree 指显式安装并从该根启动的新 CLI 会话。官方 hooks 文档另有 Claude 会话内进入 worktree 后 CLAUDE_PROJECT_DIR 不变、桌面 worktree 共享来源的条件；不能外推成新根已独立加载。M3 不承诺会话内切树或桌面自动 worktree 的隔离，入口发现实际 cwd/声明与绑定不符必须诊断，不能继续写旧根 state；A6/B2/C2 分别验证支持的显式启动方式。

普通嵌套目录中的管理命令始终需要明确 `--project <根>`。M3 不支持一个已安装 STYLE 项目根下再创建另一个 STYLE 项目根；安装和运行入口都检测祖先声明歧义并报错，防止父/子 hook 指向同一 index 后重复运行。嵌套启动目录、多个并列项目与多个 clone 则要覆盖。

在 U 内维护私有项目登记表，记录规范根、对应安装根、harness 用户配置身份及每个目标的包名，用于跨范围冲突检查。登记表不是扫描整个磁盘的保证；缺失/陈旧登记、无法读取的已登记安装、外来 STYLE handler 或不匹配的 binding 都给出冲突和修复路径，不擅自删除记录或以“未发现”认定安全。新写入共用 U 与项目的管理 guard，按规范路径排序获取，重新核对全部捕获输入；并发冲突失败，不在确认期间持锁。

新项目路线与 Claude 插件路线使用 **lock format=3**，增加显式 scope/binding 元数据（scope、root、base home、project home、harness 配置身份、入口版本和受管路径摘要）；批准身份绑定相同范围，旧程序因不支持格式先拒绝写入。现有三路线保持 lock 1/2；普通旧安装不自动迁移。新功能显式升级后不降回旧格式，切换路线必须经过普通安装预览，frozen 只恢复原根/原绑定。index 仍为 format=1；不把机器路径写入规则正文、state key 或包 schema。

## 4. 用户与项目共存

每个根只编译自己的包。不同名包可以在同一个 harness 的用户和项目范围中同时生效，各保留自己的 seq、预算、state 和统计；不承诺跨范围的总体优先级、预算合并或正文去重。报告明确列出两个活跃范围，不能把各自的预算估算说成整个会话上限。

**同一 harness 的用户范围与任一已登记项目范围禁止安装同名包**，即使版本相同也先拒绝整批，避免静态/native 和普通规则各投递一次。两个项目之间允许同名。用户安装也反查已登记项目；冲突只列范围/名字和显式卸载或改名的操作，不自动批准、迁移或清理另一根。不得通过删除全局 handler 来“解决”冲突，否则其他项目会丢规则。自定义 U 指向同一 harness 配置而已有另一 U 的 STYLE owner 时拒绝混装。

Codex 不写项目 `developer_instructions`，因为实测会覆盖用户指令。项目 adapter 将 append 静态槽位声明为不可用，沿用现有 `session.start` + compact 补发的动态降级并在 plan/approval 中披露；不能把 AGENTS.md 改作未测且语义不同的静态槽位。`replace` 沿用无槽位/回退策略，授权开关不会创造支持。Claude 项目静态 append 写 `<R>/.claude/rules/style-<包>.md`，与用户 rules 并存，按范围内所有权恢复；不迁移项目中用户自写的 CLAUDE.md。

## 5. 本地项目路线

| 路线 | 写入与加载 | 信任及诊断 |
|---|---|---|
| `codex-project` | `<R>/.codex/hooks.json`；只把对应 hook 哈希合并到用户 CODEX_HOME/config.toml。静态 append 使用上节动态降级 | 必须分别显示项目信任和 hook 摘要状态；不写 projects.trust_level，不启用沙箱旁路，不替用户接受原生 UI；规范路径之外的启动提示待处理 |
| `claude-project` | `<R>/.claude/settings.json` 的受管 hook、`<R>/.claude/rules`；不写 settings.local.json | 要求从 R 启动，子目录只保证已测静态发现，动态诊断明确提示启动条件；不改 hasTrustDialogAccepted，不用 -p 的成功认定交互信任 |

只在项目范围暴露上述路线；显式选择 user/plugin 路线与项目范围冲突时拒绝，不隐式把文件写到用户配置。用户范围继续保留现有默认路线顺序。新路线首次离线支持以已测 Codex 0.159.3 / Claude 2.1.301 为基线，低/未知版本按能力前提阻断，不以版本号替代实际信任或加载检查。

生成的普通 hook 使用 PATH 中的 `style` 与可移植项目入口；Claude exec args 使用 `${CLAUDE_PROJECT_DIR}` 定位受管启动器。Codex 启动器从进程 cwd 向上查找唯一 `.style/project.json`，有目录深度/文件大小上限，不调用 git、shell 查根或网络；找到 R 后定位 U/projects/H，核对私有 binding（包括实际 runner 身份）再进入既有 agenthooks runner。没有安装、找错根、声明损坏、STYLE_HOME 不一致均明确失败，不能退到用户 index。显式自定义 U 时，启动 harness 的环境必须解析到同一 U，doctor 报告这一前提。

发现/绑定属于 app 启动入口；输入解码、事件表、异步处理和输出仍归 agenthooks。runner 已启动时，入口失败需通过既有 codec/策略编码 hook 错误，不能用管理退出码绕过 fail-open/fail-closed；PATH 中根本没有 runner 时只能由启动器写 stderr 并返回原生进程错误，阻断能力取决于该事件/原生配置，不能承诺所有事件 fail-closed（D8 另评估）。native 命令继续直接交由原生 hook 执行，使用原生工作目录（Codex 可为子目录）及原文字节，不进入 STYLE engine；包作者须使用可移植的项目路径，依赖/权限作为能力披露。任意 shell 命令的可移植性不能由字符串猜测保证，本地绝对路径依赖必须显示为部署前提，不能被报告成已在云端验证。

用户 CODEX_HOME 中来自多个项目的 trust 表要按项目源路径隔离，不能复用当前单一 `style` 区域时把别的项目或用户信任表覆盖掉。单个项目 native 定义变化只更新对应 hash；卸载只移除该项目所属表和文件，保留原生 UI 写入的项目 trust、其他 owner、其他项目与用户配置。

## 6. Claude 云端交付

T31 支持单仓库、从仓库根启动的 Anthropic 托管会话，使用项目路线；云端插件路线不作为替代。选择 **预置固定版本 style + 显式导出批准产物**：不由 SessionStart 自动 go install、下载程序、取 Git 来源或编译用户包。

`style export --target claude-cloud --project R` 捕获本项目已批准的 lock/approval/settings/index/provenance、Claude 路线和静态/native 定义；拒绝漂移、不完整安装、未信任 link 和不支持的输出。导出不修改原锁或重新批准包。完整预览列出要提交的正文、native 命令、平台/二进制版本与依赖、文件摘要、敏感信息风险；有变化要求 --yes，同一捕获候选提交，失败回滚。

生成 `<R>/.style/cloud/{manifest.json,index.json,explain.json}` 和必要的项目文件。manifest format=1，包含目标、生成器/runner 兼容版本、来源与编译摘要、全部相对文件路径和逐文件哈希、native 定义摘要及外部依赖说明；不得写本机 lock/source/settings 路径、批准仓库、私有根或缓存。路径必须在 R 内，不接受绝对路径、`..`、symlink 或机器绑定的文件引用；`src`/诊断来源改为包逻辑相对名，不把真实路径拷贝进 provenance。沿用 `sensitive-reserved`：带 sensitive 字段的源仍由既有 schema 拒绝，D3 不启用敏感设置。普通字符串设置、正文和 native 原文不具备可靠的自动 secret 识别能力，必须完整披露供用户审阅，不能声称 export 已自动脱敏。私有安装根的独立 export receipt 记录导出 generation 与受管文件，用于陈旧检查和卸载恢复，和产物一同事务提交，不借导出改写原锁。

项目 Claude 启动器根据 `CLAUDE_CODE_REMOTE=true` 显式选择 cloud bundle；本地默认仍使用私有项目安装。云端入口核验 manifest、文件摘要和 runner 兼容性后加载预编译 index，state、stats、codec cache 与 probe 根在云端 HOME 的独立项目命名空间，不能写进仓库/共享 bundle。缺 bundle/runtime、版本不兼容或摘要漂移给诊断并沿已有 fail-open/fail-closed 协议处理，不静默回落到本机/用户安装；不因“只有静态规则还在”报告完整交付成功。

上述相对路径校验针对 bundle 路径和结构化引用，不把任意正文或 shell 原文当作可安全解析的路径清单。native 保留已批准原文和原生信任/错误语义；export 同时披露其外部命令、脚本路径及未验证依赖，不承诺任意 native shell 在另一平台自包含。A7 要有已预置依赖的 portable native 正例和缺依赖失败例；C3 必须实际验证所宣称组合。云端环境的 setup 配置由用户提供，安装 runner 的固定 release/源 revision 和校验方法写入 runbook；Go 预装或网络白名单不等于 style 已存在。

静态 rules 随仓库文件加载；导出后的本地包变化不会自动同步 bundle。doctor/export 检测 generation 不一致，要求重新显式 export；旧 bundle 的完整性不等于最新源码。卸载项目最后一个包时将已导出的受管文件纳入预览和同一事务移除，恢复外部配置；已有云端会话不强制热卸载，删除/提交后用新会话验证。多仓库、自托管、云端账户登录和缺环境不由本地 fixture 代验，C3 保持 `[?]`。

## 7. Claude 插件路线

新增用户范围 `claude-plugin`，仅支持用户添加的**本地目录 marketplace + 相对 source 的插件**。默认仍为 claude-user，不因二进制版本而自动切换。生成于 `U/adapters/claude/marketplace/`，marketplace 名为 `style-<SHA256(规范U)>`（完整摘要），其中 `plugins/style-runtime/` 包含 `.claude-plugin/plugin.json`、`hooks/hooks.json`、`scripts/style`；不生成顶层 bin/。固定载体版本 `0.1.0`，包版本/approval 独立记录；原地加载的内容以安装 generation/摘要跟踪，远程或缓存 marketplace 不在支持面。

普通 command 使用 `/bin/sh` 与 exec args `${CLAUDE_PLUGIN_ROOT}/scripts/style`；launcher 固定本次批准的 style executable 与 U/harness 绑定。native 保持原生原文、owner/tag 和更新披露。插件不把任意 rules/CLAUDE.md 自动当成静态指令；**静态规则仍由 STYLE 管理用户 `.claude/rules`**，与既有 Codex plugin 的外部静态槽位原则一致。因此禁用插件只停止插件 hook，静态规则到 STYLE uninstall 才移除；doctor 和文档必须明确，不得宣称插件禁用等于整个 STYLE 安装停用。

STYLE 只生成、核验产物并给出精确登记/卸载步骤，不自动执行 claude plugin 命令，也不直接编辑 known_marketplaces.json / installed_plugins.json 等原生数据库。用户在指定 CLAUDE_CONFIG_DIR 下手动 marketplace add，然后 install `style-runtime@<本次marketplace>`（user scope），重启并用 probe/原生 UI 验证；不得拿文件存在或 enabledPlugins 声明当作已加载或已信任。

claude-user 与 claude-plugin 在同一用户安装根是互斥 hook 载体；切换要求普通 install 的明确路线预览，合并“移除旧载体 + 生成新载体”一次事务。已登记/启用的插件须先由用户原生禁用/卸载并复核，STYLE 才移除/切换源目录，防止旧插件与新 settings 同时运行；状态无法核实则停止变更、给下一步命令。等待登记/卸载属于 `registration-required`，退出 1；本地生成成功但尚未登记的状态单列，不记 probe 成功。多个 STYLE 包共用一个载体，卸载非最后包只重编译并保留载体；最后包卸载仍遵循登记检查。

STYLE 保证自己文件/受管区的字节、权限和失败恢复；用户执行原生 CLI 后留下的空键、缓存与 orphan 标记按原生生命周期管理，报告其存在，不替用户删原生数据库。A8 的“无残留”明确指 STYLE 受管效果/文件和新会话无 STYLE hook 回调，不把原生缓存残留藏起来。项目范围插件登记、本地 --plugin-dir 临时加载、claude.ai/Cowork 插件分发均不纳入此路线，项目/云端继续用前两节。

## 8. 职责与事务

| 层 | 本次需要的变化与边界 |
|---|---|
| app | 范围解析、项目登记/binding、跨范围冲突、lock 3、cloud 导出/入口、安装管理 guard 与候选事务；不在热路径读包或取得来源 |

agenthooks 必须补足 Codex ScopeProject 的 Target.Dir（项目配置）与 ConfigDir（用户 trust）拆分，以及按源路径的 owner trust 合并/删除。保留原 ScopeUser/ScopePlugin 的路径和字节；不为新项目别名盲改既有规范化。Claude renderer 增加可移植的 exec argv/插件 launcher 支持；同一 hook 定义的哈希、owner 和原生披露用同一数据源。新增字段默认零值保持既有渲染，双 module 的配置、owner、移除、故障和协议回归必须一起验证。

复用 D2 捕获一次、detached 确认、stale 检查、stage/exchange、ApplyFiles 和逆序恢复。跨 U/private project、R 及 harness 用户配置的文件归同一计划，逐处写入失败必须回滚并保留失败备份；用户执行原生登记步骤不纳入这次文件事务。声明、登记表与 lock 不得先于实际安装对外宣称成功。guard 只协调合作管理进程，不宣称跨文件掉电原子性。
